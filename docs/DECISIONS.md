# 关键设计取舍

本文记录 swapdesk 中会影响结果可解释性与可复现性的设计决策。

## 1. 影响图的范围与建模

登记表以「对象 ID」为全局主键，源、任务、下游对象、口径共享同一个 ID 空间。
影响图按以下边构建：

- `task.source_refs`：源 → 任务；
- `downstream.upstream_refs`：源/任务/下游 → 下游；
- `lineage.from_ref → to_ref`：显式字段血缘；
- `metric.source_refs`：源/任务/下游 → 口径。

这样做的原因是：同一份血缘可能同时出现在登记字段与 lineage 边中，直接依赖与间接血缘
需要统一处理。任务→下游的链式传播不要求每一跳都在 lineage 中有边，登记关系本身即可传播；
lineage 负责补充跨对象、字段级证据。

**取舍**：没有引入图数据库，内存邻接表（节点数在演示规模内）足以确定性重放；
不实现更复杂的图算法（如最小割、关键路径），因为本期目标是变更识别而非性能优化。

## 2. 直接 / 间接与多源任务

最短路 BFS 从全部待下线源同时出发。某目标第一次被访问的路径即报告路径；一条边为直接，
两条以上边为间接。路径以字典序邻居顺序展开，起点按源 ID 排序，因此结果可复现。

多源任务只撤换部分源时，`partial=true`，并列出 `remaining_sources`。字段兼容判断不是
「逐个替代源必须覆盖任务全部字段」，而是「替代后的有效源集合字段并集必须覆盖」。
否则像 `task-orders-enrich` 这种从另一个源取 `device_id` 的任务会被误报 blocking。

## 3. 环检测与截断

依赖环使用稳定 DFS：节点、邻居均排序；发现回边后把环旋转到字典序最小节点，再放入集合去重。
告警中附完整节点序列。传播仍用普通 BFS，靠 visited 集合截断。

**取舍**：不枚举所有初等环，也不在环上做启发式修复。规则是「报告 + 截断 + 其余路径继续」，
因为迁移计划不应因一个环而无限递归；真实修复需要人工确认。

## 4. 冲突分级与阻断

- `blocking`：计划不能生成/执行——替代源缺失、替代源自身、任务必需字段在替代后缺失、
  必需口径字段断裂。
- `warning`：需要关注但不阻断——窗口重叠、类型改变、已退役源、必需口径仅经血缘受影响。
- `info`：记录性提示——多源部分撤换、仅血缘受影响的任务、零长度窗口。

替代源在 schema 阶段允许尚不存在，因为「替代源是否存在」本身就是 F3 的业务判定；
若在 YAML 校验阶段直接拒绝，就无法针对缺失替代源给出稳定的 `C_REPLACEMENT_MISSING` 证据。
撤换请求的待下线源则必须在分析加载时已登记，否则报 `E_REF_UNKNOWN_SOURCE`。

## 5. 计划批次与拓扑

步骤按依赖语义分四级：任务引用（1）→ 下游引用与血缘（2）→ 口径（3）→ 退役源（4）。
每一级内部按 `target_type`、`target_id`、`action` 排序；跨级步骤依赖所有更低级的步骤。
每级是一个 batch，batch 内按 `max_parallel` 切分 `sub_batches`。

**取舍**：没有采用通用 DAG 调度器，而是固定等级 + 显式依赖。原因是动作语义始终是
「先改所有引用，再退役源」，固定等级更容易审计且不会因环产生计划死锁。`step_id`
在排序后按 `step-0001` 形式分配，保证相同输入的计划逐字节一致。

## 6. 状态与哈希口径

World state 仅包含会影响引用/可用性的字段：

```
sources:    status, fields
tasks:      status, source_refs
downstream: status, upstream_refs
lineage:    from_ref, to_ref
metrics:    status, source_refs
```

`name`、`owner`、`definition` 等展示属性不进入状态哈希。哈希算法：
对规范化 JSON 做 UTF-8 SHA-256。规范化时键排序、紧凑分隔符、浮点归一化；
计划/分析中不写入当前时钟。执行时间戳单独存台账，可用 `--timestamp` 固定。

**取舍**：使用内容哈希而不是数据库自增 ID，避免“换个机器就不一致”。步骤产物状态快照
用于验证计划后置断言，它比只存哈希更占空间，但让复核可以在不重放动作的情况下检查证据。

## 7. 台账、run_id 与幂等

`run_id` 由计划哈希前 16 位派生；相同输入重跑命中同一运行。步骤以
`(run_id, step_id)` 为联合主键，写入采用“成功即跳过”，所以重复执行不增加尝试次数。
每个步骤成功后立即落盘 state、写产物并更新台账；`--stop-after` 只影响本次调用推进的步数。

**取舍**：没有实现数据库事务跨步骤的分布式原子性；这是本地 mock 执行器，目标是可重入、
可审计。台账与状态文件分离，便于人工查看与损坏定位。

## 8. 回滚

回滚只基于台账中已成功步骤，倒序生成反向动作；引用类直接交换 `before/after`，
退役类变成恢复源状态。回滚写入独立 run（`rb-<source-run-id>`），保留原执行台账。
完成后比较最终状态哈希与原始 `initial_hash`，输出 `restored` 和（不满足时的）原因。

**取舍**：不做“时间旅行”式状态重建，而是把反向动作显式写入计划并再次走同一执行器，
这样回滚本身也经过台账、产物与 verify，和正向执行同等可审计。

## 9. 报告与服务

Markdown/HTML 报告从同一份分析、计划、执行和复核对象渲染，避免两套事实来源。
HTML 是单文件，CSS 内联，不引用字体/图片/CDN。报告服务只绑定 loopback，仅 GET，
并在路径拼接前拒绝 `..`、反斜杠、空名和绝对路径；随后仍用 `safe_join` 做第二道边界检查。

## 10. 演示重置与可重复性

`demo` 固定输入生成器、固定 seed、固定时间戳，并直接把结果写入 `--workdir`
（默认 `./var`），使默认 `serve` 能读取 demo 报告。运行按计划哈希复用同一 run，
步骤成功即跳过，因此重复 demo 的 plan/analysis/HTML/Markdown 与台账核心字段一致。
demo 不主动删除工作目录中的其他内容，避免误删用户产物。数据登记表与生成器输出保持同源。

## 11. 明确不纳入本期

真实采集、网络请求、DWH 元数据读取、图数据库/前端可视化、跨口径数值比对、分布式调度、
多用户权限、邮件/webhook 通知、学习型推荐均不实现；见 README 的“已知限制”。
